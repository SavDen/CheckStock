CHECKSTOCK: ШПАРГАЛКА ДЛЯ ЗАЩИТЫ

Что делает продукт
Менеджер видит, где лежит товар, что обещано клиенту, что можно отправить и что уже едет. SKU — артикул, ФФ — склад фулфилмента. FBS — отправка клиенту со своего ФФ, FBO — поставка на склад маркетплейса.

Из чего состоит
Браузер показывает экран и отправляет команды. FastAPI принимает команды и проверяет формат данных. Сервис складских операций проверяет бизнес-правила. PostgreSQL хранит товары, склады, остатки, движения и историю.

Пример
Нажали «Отправить 3» → браузер отправил команду → сервер проверил склад, статус и количество → база сохранила списание, новый статус и событие → браузер получил обновлённые данные.

Как хранится учёт
Остаток хранится для конкретной пары товар/склад. У каждой партии в движении есть тип, количество, источник, назначение и статус. История хранит уже совершённые действия. Движение и запись истории — разные вещи: одно движение может пройти несколько этапов и создать несколько событий.

Три количества
Физически: сколько лежит на складе, включая резерв.
В резерве: сколько из лежащего уже обещано под FBS.
Доступно: физически минус резерв.
Резерв нельзя прибавлять к физическому остатку: получится двойной учёт.

Сценарий с органайзерами
1. Север 10, Юг 6.
2. Приход 5 на Север: Север 15, Юг 6.
3. Резерв 3 на Севере: физически 15, доступно 12, резерв 3.
4. Отправка FBS 3: Север 12, Юг 6, клиенту едут 3.
5. Попытка FBO 14 с Севера: отказ, потому что локально есть только 12.
6. FBO 4: Север 8, Юг 6, маркетплейсу едут 4, клиенту 3.
7. Перемещение 2: Север 6, Юг пока 6, между ФФ едут 2.
8. Приёмка: Север 6, Юг 8. FBO/FBS по 4 и 3 учитываются отдельно.
9. Архивирование Севера: его 6 органайзеров и 5 контейнеров сохраняются.

Три разных механизма защиты
Транзакция: или сохранится вся операция целиком, или не сохранится ничего.
Блокировка: две разные команды не смогут одновременно использовать один старый остаток. Вторая ждёт первую.
Идемпотентность: повтор одной команды не выполнит её второй раз. Это защита при двойном запросе или потере ответа.

Пример конкуренции
На складе 10. Два менеджера хотят зарезервировать по 7. Без защиты оба могут увидеть 10. С блокировкой первая команда оставит 3 доступных, вторая после ожидания увидит 3 и получит отказ.

Почему одной выключенной кнопки мало
Запрос можно повторить без браузера или при сетевом сбое. Правила должны защищаться на сервере. В приложении есть блокировка кнопки, ключ идемпотентности и безопасные переходы состояний.

Что именно блокируется
Строка магазина в PostgreSQL, а не весь сервер и не вся база. Все складские изменения этого магазина идут через этот протокол. Для одного магазина это простой компромисс; для высокой нагрузки блокировки нужно разделить по SKU/складу с фиксированным порядком захвата.

Почему архивирование
Удаление справочной записи не перемещает физический товар. Остатки должны остаться видимыми. Новые приходы и продажи в архив запрещены; вывоз и завершение старых обязательств разрешены. Ранее отправленную партию можно принять даже после архивирования склада назначения.

Где FBO после приёмки
В завершённых движениях с назначением на маркетплейс. Отдельного полноценного модуля учёта остатков маркетплейса в этом прототипе нет. ФФ повторно не увеличивается.

Почему история не меняется при переименовании
В событии сохраняется название склада на момент действия. У справочника и исторической записи разные задачи.

Как проверить, что товар не потерялся
Для каждого SKU все приходы равны физическому остатку всех ФФ плюс товар в пути плюс завершённые внешние FBO/FBS. Завершённое внутреннее перемещение не прибавляется повторно — его товар уже находится на складе назначения. Резерв уже входит в физический остаток.

Роль технологий
Python — язык серверного кода.
FastAPI — принимает HTTP-запросы и описывает API.
Pydantic — проверяет структуру входных данных: например, количество должно быть целым и положительным.
SQLAlchemy — работа с таблицами, запросами и транзакциями из Python.
PostgreSQL — постоянное хранение и транзакционные блокировки.
Alembic — последовательные изменения схемы базы, чтобы одинаково создавать её с нуля.
Pytest — запуск тестов.
Docker Compose — описание совместного запуска приложения и PostgreSQL.

Где смотреть код
app/main.py: маршруты API и общая обработка команды с Idempotency-Key.
app/service.py: складские правила, проверки и смена статусов.
app/models.py: таблицы и ограничения.
app/schemas.py: формат входных запросов.
app/seed.py: повторяемая загрузка исходных товаров и остатков.
alembic/versions/001_initial.py: создание структуры базы.
tests/test_inventory.py: складские сценарии, повторы и конкуренция.

Что подтверждено
23 интеграционных теста на PostgreSQL прошли. Основные действия выполнены через интерфейс. Штатный локальный запуск проверен. Docker Compose подготовлен, но контейнер приложения здесь не запускался. После публикации GitHub Actions успешно выполнил проверки, включая 23 теста на PostgreSQL 17.

Что не обещать
Нет авторизации, нескольких магазинов, API WB, частичной приёмки, возвратов и производственной нагрузки. История не редактируется через API, но администратор БД технически может изменить её напрямую. Нельзя говорить, что прототип уже готов к публичной промышленной эксплуатации.

Как объяснить ИИ
ИИ помог подготовить код, тесты и документацию. Проверка результата — отдельная работа: реальные операции через интерфейс и интеграционные тесты. На защите важно самостоятельно объяснять правила, числа и компромиссы. Не утверждай, что лично написал или проверил часть, которую ещё не разобрал.
